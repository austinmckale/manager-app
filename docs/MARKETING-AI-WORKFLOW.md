# Marketing AI: operation and setup

Open **Marketing → AI processing & submissions needing context** (`/marketing/delivery`). The worker runs independently of Codex as the Windows scheduled task **RHI Pros Local Marketing Worker**. Windows must be signed in and the PC awake. The website saves uploads while the PC is offline. Closing this chat does not stop an installed worker.

## First use

1. Choose **Hybrid**. Voice transcription runs locally; photos, notes, generation and claim checking use the OpenAI Responses API. The configurable initial model is `gpt-4.1-mini` (override with `MARKETING_OPENAI_MODEL`). Ollama mode stays entirely local. Manual mode does not generate automatically.
2. Add `OPENAI_API_KEY` to the installed worker folder's **private** `.env.marketing-ai.local` file. This separate file holds only AI configuration and loads before the main worker environment on each cycle. Do not paste keys into chat, public frontend configuration or a committed file. An API account with billing is separate from a ChatGPT subscription. The UI reports key presence, not billing/account validity; verify with a test.
3. Keep automatic processing **Off**, save settings, then click **Run one test cycle**. This consumes one pending submission, including test uploads. If none is pending, it checks a saved draft. On an individual saved draft, **Run AI checks** requests that exact version without enabling automatic generation. A held submission's correction form requests a test of that exact submission.
4. Inspect the evidence and generated copy. Then enable **Process new uploads automatically** and save if desired. Saving Off cancels an unclaimed test; a running request can finish. Settings are checked by the worker each cycle, normally about one minute apart when idle; in-progress work or failures can delay the next cycle.

The initial API limit is **60 calls per UTC day**, shared by generation, review and retries. Each image needs a separate inspection call. A successful new pack normally takes N+3 calls (N photo inspections, note extraction, writing and claim audit), plus any retry. Editing copy requires new checks. Calls are reserved atomically before sending; timeouts count because the provider may have processed them. Token usage is recorded when returned. This is a request cap, not a dollar guarantee. Configure provider billing alerts/limits too. Missing credentials, refusal, incomplete output, invalid JSON and unavailable models never count as passing checks.

## Evidence and approval

Every selected photo is inspected. Exact source quotes are retained separately from model summaries. Microphone tests and interface feedback provide no job facts. Irrelevant photos, conflicts, visible privacy issues, missing inspections and unsupported claims hold a submission with specific reasons. Choose **Company personality / team life** only when the owner explains that intent; a dog image alone never establishes construction work.

RHI Pros did all the work shown in its job photos (owner's direction, October 20, 2026). A post may say so, and no check asks the notes to prove it: the copy check that blocked "we built" without a first-person note is gone, and a fact-check finding that only doubts who did the work is cosmetic (`cosmeticFinding`). A finding that also questions a town, offer, date or contact detail still blocks.

A photo concern holds a draft only for privacy (a person or face, a house number or address, a license plate, a readable name, phone number, email or document) or a reason not to post it (unrelated to the job, "do not publish", unsafe). Commentary such as "lighting is dim", "cabinets look finished" or "dishwasher fronts are not paneled" does not (`blockingConcern` in `src/lib/marketing-evidence.ts`); the owner looks at every photo before approving. A quote the reader filed under the wrong source, or copied with other capitals or spacing, is kept under the source that has it, in that source's exact words (`mergeNoteReads`). This is what kept website past-job packs at zero facts.

Sources are rechecked before saving a generated draft. The exact public fields must match the reviewed fields. Passed generation checks become a review of that immutable draft and source hash; they do not approve it. Owner approval remains separate. Editing text, changing evidence or replacing a version invalidates the applicable review. Older reviews require the new evidence policy before approval/publishing. The existing publishing service still checks exact owner approval.

## The review page

A draft's **Review & approve** page shows only what Buffer posts, in four steps: **Photos** (numbered; photo 1 leads), **Post text** (the Facebook & Instagram post and the Google Business update, each with **Keep**, plus a collapsed preview), **Improve with AI**, and **Check and approve**. Ad drafts, the town, the service and the pack name are not posted, so they sit under **More**, with Ryan's audio, transcript and notes and the ChatGPT/Claude round trip. Only the two posted captions are checked: the approval gate, the publishing gate and the page use `postedCopyChecks` (`src/lib/copy-checks.ts`), which also warns when the Google Business update repeats the Facebook post.

## Check with AI before approval

**Check with AI** is the last step before approval. With unsaved changes, including text or photos imported from ChatGPT or Claude, it becomes **Save and check with AI**, which saves a new version and queues the check on it in one request (`save` with `check: true`). The local worker reads every photo and note again, then the writer model fact-checks the Facebook/Instagram post and the Google Business update.

When a post fails, the worker runs the fix loop on the owner's current text (`proposeCaptionFixes` in `scripts/local-write-loop.ts`) and stores only the posts it improved, with how many problems remain, in the review record's `fixes`. Nothing is applied. The page lists each suggestion with **Use this** and **Use all**; using one puts it in the editor, and checking again saves and checks it. Problems name photos by number, not id. Owner approval is still separate.

## Keep and rewrite with AI

Each posted caption has a **Keep** toggle (stored per version as `marketing.caption.locks` and carried to the next version on save); typing in a caption keeps it. Under **Improve with AI**, type what should change (or tap a quick ask such as Make it shorter, which adds to the box) and press **Rewrite with AI**. That queues a caption revision with `mode: "regenerate"`, the kept posts' text and the typed note. The worker (`scripts/local-caption-revision.ts` → `regenerateUnlocked`) rewrites only the posts that are not kept, with the kept one as fixed context, then fact-checks and fixes them like any draft. It uses the evidence from the latest completed AI check on this version or the versions it was saved from (`scripts/local-regenerate.ts`); a never-checked draft has its photos and notes read once (`freshEvidence`). The page fills only the boxes that are not kept and offers Undo.

A note that asks to remove something is enforced, not just passed on (`removalTargets`): "remove the dishwasher description", "don't mention the dishwashers" and "take out the part about the microwave" each name the thing to drop. Facts that mention it are not given to the writer, the writer is told to leave it out (`leaveOut`), a rewrite that still mentions it is sent back with that reason, and on the retry any sentence that still mentions it is cut. Style asks ("cut it down to two sentences", "remove the last sentence") are not read as things to drop. A rewrite is also sent back when it copies a kept post or when the Google Business update repeats the Facebook post.

The fact-check accepts field names prefixed with `publicFields.` and checks captions the checker skipped in a second, smaller call. Written captions are rejected before checking when they contain Chinese, Japanese or Korean characters or when a headline or Google description ends on a dangling word, and the retry message names the problem.

## House voice

RHI Pros did all the work in its job photos, and the posts are about the work itself, with some life (owner's direction, October 20, 2026). Every writer call (new packs, suggested fixes, rewrites) receives `houseVoice` (`HOUSE_VOICE` in `scripts/local-voice.ts`): Ryan telling a neighbor about a recent job, warm and specific; say RHI did it lightly or not at all; bring the work to life with materials, colors, textures, light and craftsmanship; homeowner words, no slogans or hype, never the word scope; creative in how it is said, never in what it claims. It also receives `voiceExamples`, the owner's three newest approved Facebook/Instagram posts, to match their tone without reusing their facts. The writer system prompt says the same, and first drafts are written at temperatures 0.55 and 0.8 (fix rounds stay at 0.3); the fact-check still removes anything the facts do not support and does not fail a post for its style. The ChatGPT/Claude prompt carries the same direction.

## Past jobs

`/marketing/past-jobs` lists the website's gallery projects from `src/lib/website-project-catalog.ts`, which `node --import tsx scripts/sync-website-projects.ts <website repo>` rebuilds (retired and gallery-hidden projects and the website's hidden photos are left out). **Make a post from this** (`/api/marketing/past-jobs`, `src/lib/past-jobs.ts`) copies that project's website photos once into the internal job "Website past jobs" (tagged `website-project` and `website:<slug>`, stage AFTER unless the path says before or during), saves a pack with `source: "website-project"` whose captions start from the website's published summary and solution (`src/lib/past-jobs-copy.ts`), and queues the AI check without taking the single test slot, so the worker checks packs in order. The page shows each project's newest version and whether it is approved. When Ryan has sent no photos for 7 days, the inbox suggests one past job (`suggestPastJob`): not sent to Buffer in the last 90 days, in season, the same pick Monday to Sunday.

## ChatGPT / Claude round trip

Open a saved draft's **Review & approve** page, then **More → Ask ChatGPT or Claude**. **Download the bundle for ChatGPT** and follow its START-HERE.txt: attach every photo, `review-prompt.txt` and `raw-input.json` to the chat and say "Follow review-prompt.txt". The bundle contains private notes and voice transcripts; inspect what you share. The prompt (`chatReviewPrompt` in `src/lib/marketing-handoff.ts`) always asks, in order, for: (1) a careful study of every photo at full size, covering what it shows, its quality and every imperfection, returned as `photoAnalysis`; (2) choosing and ordering the photos; (3) cleaning them up if the chat can edit images (ChatGPT can, Claude cannot): straighten, crop, fix exposure and color, remove temporary things such as stickers, labels, protective film, packaging, tape, tools, cords, trash and clutter, and blur faces, house numbers and plates. It may finish an obviously incomplete detail only to match the finished work right around it, such as covering exposed panel-ready dishwasher fronts with panels that match the cabinets; it never adds features or changes materials, colors or layout. Every change is listed in `photoImprovements`, and edited files are named `edited-` plus the original name; (4) writing the two posts, Google shorter and different; (5) returning one ZIP, `rhi-import.zip`, holding `import.json` and the edited photos.

**Choose the ZIP ChatGPT gave back** imports it in one step: the browser opens the ZIP (JSZip), imports `import.json` (or the only other JSON file) as unapproved edits, then matches each image named `edited…` to its original by the id or photo number in its file name and adds it. The message under the control says what came in and what was skipped. If the chat only replied with text, **The chat replied with text, or sent photos separately** takes the whole pasted reply (**Import the text**) and photos downloaded one by one.

The text import accepts the whole reply: text around the JSON, a ```json block, smart quotes and trailing commas are fine (`extractReplyJson`). A missing field keeps the current text, a field over its limit keeps the current text, over-limit or repeated ad lines are dropped, and extra fields are ignored; the editor lists each of these. A reply for an earlier version of the same draft imports with a note. Only a reply that names a different draft and shares none of its photos is refused. Source notes, photo notes, the landing page, approval and photos that are not on the version are never taken from a reply, and the publication block still applies.

Each edited photo is shrunk in the browser to 2400px JPG; `/api/marketing/review/edited-photo` re-encodes it without metadata and stores a new photo tagged `chat-edit` and `edited-from:<original id>`, with `derivedFromAssetId` pointing at the root original so the notes and voice still load. The original is never changed. Saving accepts an edited copy only when the photo it replaces is on that version. Check the photos against the listed changes, then **Save and check with AI**; the check inspects the edited photos. Manual mode uses Ollama for explicitly requested checks; it does not start automatic generation.

## Local models and the fix loop

Local mode uses two models. `INTAKE_OLLAMA_MODEL` (default `qwen3.5:4b`) reads notes and photos, which are many short calls. `INTAKE_OLLAMA_WRITER_MODEL` (set to `qwen3.5:9b` in the worker's `.env.marketing-ai.local`) writes, fixes and fact-checks, which are a few calls where quality matters. Caption rewrites also use the writer. If the writer model is not downloaded, the reader writes instead (`src/lib/local-models.ts`). Measured on this RTX 3070 on October 18, 2026: both run 100% on the GPU at 8K context; the 9B writes about 32 tokens/s against 81 for the 4B and uses about 7.5 of 8 GB with the desktop running. A game holding GPU memory pushes the 9B partly onto the CPU, so turn local AI off with `RHI AI` before gaming; Off unloads both.

Writing is a loop (`scripts/local-write-loop.ts`). Local mode writes two versions at different temperatures and fact-checks each in a separate pass; Hybrid writes one to save paid calls. The version with fewer problems gets up to two fix rounds: the fact-check's findings go back to the writer, which must remove unsupported claims rather than reword them. A checker that skipped the exact text is asked again instead of triggering a rewrite. Only a draft that still has problems after the last round is held for the owner, with those problems listed. Passing the loop is still not owner approval.

Several reading rules keep good jobs from stalling before the writer runs. A concerns or conflicts entry that only says there is nothing wrong ("None", "No visible privacy concerns") is not a hold reason (`isNonConcern` in `src/lib/marketing-evidence.ts`), and a photo concern holds only for privacy or a reason not to post (see Evidence and approval). The "what is missing" pass only runs, and only holds, when the notes gave no usable facts; with facts present it invented demands such as permit approval and inspection reports. Even then it never asks for paperwork or numbers: demands for permits, inspections, warranties, receipts, dates, model or serial numbers, spec sheets, brands, finish codes, measurements, prices, the town or customer details are dropped. Measured October 18, 2026 on the Bethlehem staircase project photo and its published description: before these rules it was held with six such reasons; after, it read in 9 seconds on the 4B and passed one write and one fact-check on the 9B in about 165 seconds.

## Running and testing locally

Before pointing the scheduled task at a release folder, run `node --import tsx scripts/worker-preflight.ts` inside it. It loads every worker module, checks Ollama has the reader model and reports a missing writer, and makes one read-only database query. A release with a missing file fails there instead of failing every cycle in the background; the worker's status file now names that case too.

The installer `scripts/install-marketing-worker.ps1 -WorkerRoot <release-folder>` points the scheduled task at that release. It requires installed dependencies and the private worker environment file. `scripts/marketing-worker-status.ps1 -WorkerRoot <release-folder>` shows process status. The app uses a separate database heartbeat to show when this worker version last checked in. These paths must refer to the installed release, not an unrelated development checkout.

- `node --test scripts/check-marketing-evidence.mjs scripts/check-content-review.mjs scripts/check-generation-queue.mjs scripts/check-marketing.mjs scripts/check-worker-bugs.mjs`
- `node --import tsx --test scripts/check-write-loop.mjs scripts/check-past-jobs.mjs`
- `npx tsc --noEmit --incremental false`
- `npx tsx scripts/evaluate-marketing-evidence.ts <private-source.json>` performs read-only local evaluation without database writes, paid calls or notifications. Treat actual model evaluations separately from mocked regression tests.

## Social delivery

Open /marketing/buffer. BUFFER_API_KEY is a private Vercel Production secret; redeploy after changing it. Check the connection, then save the intended channels.

On an approved version's Review & approve page, choose **Send to Buffer**. Review the exact channel text and choose its photos. Facebook/Instagram allow up to 10 selected photos; Google Business uses one. The default saves unpublished Buffer drafts. The optional **Add to Buffer queue** requires an explicit acknowledgement that Buffer may publish using its queue schedule. Buffer runs in the cloud; the PC does not need to stay on after queueing.

The server revalidates current owner approval, evidence hash, org/job photo ownership and currently available saved channels before sending. It rechecks approval after preparing media. Signed private media links last seven days for provider ingestion and are never returned in delivery history. A unique durable claim per org/version/channel blocks duplicate sends, including double clicks, partial failures, timeout retries and switching draft/queue. If a version already exists as a Buffer draft, schedule that existing post inside Buffer. Unknown or rejected attempts are not automatically resent; inspect Buffer and reconcile them manually.

Delivery history stores Buffer post IDs and distinguishes draft, queued, sending, failed and published. **Refresh status** reads Buffer directly; only sent posts with sentAt are labeled published. Queue acceptance is not proof of social publication. Refresh is manual; no background status polling or webhook is installed. Posting limits, expired social connections and Buffer queue pauses may prevent delivery and should be resolved in Buffer.

**Create private test drafts** uses only fixed test text and the public RHI brand image. It creates at most one test per channel and reads the post back, verifying draft status, text, channel and image. It never queues or publishes a test. Keep test drafts unpublished.

Buffer regression checks: node --test scripts/check-buffer-setup.mjs scripts/check-buffer-delivery.mjs

## Video scope

Video uploads with embedded voiceovers are not supported by the marketing evidence pipeline yet. They require audio extraction/transcription, timestamped frame inspection across the full clip, audio/visual claim comparison and review of the exact publishable clip. A passing photo workflow does not imply video support.
